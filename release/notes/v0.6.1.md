Lightspeed v0.6.1 adds Microsoft Entra workload identity for Azure Blob storage and for PostgreSQL logins from the Runtime and Platform, so Azure deployments can run without account keys, SAS tokens or stored database passwords. It also reduces how often the Runtime and Platform reconnect to PostgreSQL.

**Compatibility and upgrade**

This is a `restart-in-place` release: `scripts/release/workflow-compat.sh v0.6.0` reports `restart-in-place`, so existing sessions continue on their current Temporal namespace.

Nothing is converted. Runtime schema revision remains **14**, Platform schema revision remains **4**, the public API protocol remains `lightspeed.agent.api.v1`, and envd and controller protocols remain **4**. Stored objects, keys and prefixes stay valid when a deployment moves to workload identity.

Restart the Runtime and Platform with matching images from this release. Existing settings keep working without changes.

**Azure Blob storage**

- Set `LIGHTSPEED_OBJECT_STORE_AZURE_AUTH_MODE=workload_identity`, with `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_FEDERATED_TOKEN_FILE` and optionally `AZURE_AUTHORITY_HOST`. The identity needs a data-plane role that can read, write, list and delete blobs in the container.
- The mode rejects a configured access key or SAS token and an HTTP endpoint, including loopback, and never falls back to another credential. `access_key` and `sas_token` are also accepted as explicit modes. Leaving the setting unset selects whichever single static credential is present, as before.
- A wrong token path or a missing federated credential appears at the first Blob operation rather than at startup. In this mode, errors keep only identifiers such as `AADSTS` codes, storage error codes and request IDs, so look up further detail in the service's logs using those IDs.

**PostgreSQL**

- Set `LIGHTSPEED_POSTGRES_AUTH_MODE=workload_identity` for the Runtime and `LIGHTSPEED_PLATFORM_DATABASE_AUTH_MODE=workload_identity` for the Platform. Both default to `password` and use the same `AZURE_*` settings.
- The database URL must name the identity as its user, hold no password and set `sslmode=verify-full`. The user is the identity's name, not its client ID, and an Entra administrator must first create a role for it. See [deployment configuration](https://ls.bot/docs/deployment/configuration/) for the SQL.
- Both processes need Microsoft Entra to open connections at startup. During a later outage they can still open connections until the current token expires, and they keep using the ones already open.
- Temporal is configured separately and still uses its own password.

**Connection pools, in every authentication mode**

- The Runtime keeps 2 connections open when idle and recycles connections after 1 hour instead of 30 minutes.
- The Platform keeps idle connections for 10 minutes instead of 10 seconds, retains up to 2, recycles connections after 1 hour and enables TCP keepalive.
- Losing an idle connection no longer ends the Platform process.
- Each process now holds connections for longer, so check that the total stays under the server's `max_connections`.

**Validation limits**

Workload identity has not been run against real Azure services, so treat the first deployment as acceptance testing. The real Entra exchange, Azure's token validation and connection cost on a real server are all unproven. `azure_blob_live` and `azure_postgres_live` cover those from a federated workload.

Local validation ran the real Blob and token clients against a TLS fake of Entra and Azure Storage, covering wire content, token rotation, certificate and hostname rejection, failed authentication and redaction. The Platform's Azure credential ran through a scripted transport. A rotation test against a real PostgreSQL role showed the old password refused, new connections using the renewed token and an open connection still working. The Platform's workload identity path has not run over TLS.
