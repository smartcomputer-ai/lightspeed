Lightspeed v0.5.0 adds JavaScript code mode for composing session tools, queued-message steering, and a new environment protocol and lifecycle model. It also introduces session soft deletion and admin purge, tighter session configuration permissions, and improvements to workspace and setup interfaces.

**Breaking changes and compatibility**

- This is a coordinated breaking upgrade from v0.4.0. Runtime schema revision is **12** (previously 10). Migration 011 adds session soft deletion; migration 012 irreversibly resets **only environment-owned database records** and installs the new environment model. The exact migration 005 shipped in v0.4.0 is retained, so its existing ledger checksum validates.
- The reset deletes environment providers, universe provider bindings, registration keys, environments, incarnations, and environment credential bindings. Provider credentials stored in those environment records are lost. Referenced auth secrets, auth providers and grants are not deleted. The migration does not reset universes, sessions, accounts, Platform data, VFS, blobs, or Temporal persistence. Database preservation does not make old environment references or workflow payloads compatible.
- The former environment protocol 2 is replaced by two exact-match protocols: **envd 4** (data and registration) and **controller 4**. Upgrade runtime, provider controllers and daemons together, including baked-in VM images. Release manifests replace `environmentProtocolVersion` with `envdProtocolVersion` and `controllerProtocolVersion`.
- Environment lifecycle now uses `provisioning`, `open`, `closing`, `closed`, and `failed`; display status is derived from lifecycle and provider observations. Incarnations and binding IDs/revisions are removed. Providers own power, idle, wake and ingress policy. Power and ingress API operations are synchronous pass-throughs; idle policy is a template default with an optional create-time override.
- `deployment/environments/adopt` and `environments/idle-policy/put` are removed. Update integrations for the regenerated API, CLI, registration receipts, provider bindings, cursor-based environment lists, and process/job/transfer contracts. Receipts no longer contain `incarnationId`. Environment transports are WebSocket or Unix socket; the old HTTP, stdio and SSH transports are removed. Protocol 4 also removes process notifications, `fs/copy`, `fs/capture`, `fs/materialize`, job artifacts, `job/list`, and `process/resize`.
- `LIGHTSPEED_ENVIRONMENT_PUBLIC_URL` is removed. A non-loopback environment gateway needs `LIGHTSPEED_PUBLIC_BASE_URL` or `LIGHTSPEED_ENVIRONMENT_REGISTRATION_URLS` for the signed registration origin. Run exactly one `environment-gateway` replica; API gateways can still scale. envd's default state directory moves to `$XDG_STATE_HOME/lightspeed-envd`, falling back to `$HOME/.local/state/lightspeed-envd`; review explicit `LIGHTSPEED_ENVD_STATE_DIR` settings and service permissions.
- Contributors can create sessions from existing profiles or universe defaults, but session configuration and per-message model/reasoning overrides require an Operator or Admin. Session close, delete and retention permissions are distinct. Review scoped service keys for the new `session/delete` and `deployment/sessions` method groups.
- Platform deletion and automatic retention now soft-delete closed sessions. Platform admins can separately purge retained history; there is no automatic purge or restore action. Direct `session/delete` and `lightspeed session delete` remain permanent by default; request `softDelete` or `--soft-delete` explicitly when retention is intended.
- The public API protocol identifier remains `lightspeed.agent.api.v1`. Platform schema revision remains 4 with baseline `0000_platform_baseline`. These unchanged values do not promise compatibility with old environment contracts or workflow histories. Use matching clients and components from one release manifest.

**Supported v0.4.0 upgrade procedure**

This procedure supports a ledger-valid v0.4.0 database with an intentional loss of environment-specific state. Rehearse against isolated copies before changing an installation with valuable data. It does not support databases that recorded the rewritten development version of migration 005: those checksums must still be rejected. Do not edit ledger rows to bypass that rejection; retain those databases and establish a separate reviewed conversion.

1. Record the old release and configuration. Inventory providers, bindings, registration policies, environment credential bindings, attached environment IDs, provider target IDs, machine disks and external effects. Preserve secrets and configuration needed to recreate access. Obtain a coordinated recovery set covering runtime and Platform databases, Temporal, object storage, stable secrets, and relevant machine/connector state. The reset cannot be undone by changing the executable back.
2. Restrict ingress and stop new work from clients, connectors, bots and schedules. With the old runtime still available, drain or cancel environment jobs and affected session runs. **Terminate remaining in-flight `EnvironmentJobWorkflow` executions using Temporal administration before new workers start**: their history types changed. Inspect parent sessions and reconcile their pending work; do not rely on replay of old environment-job histories. Temporal termination alone does not stop machine processes or undo their effects. Inspect and stop those separately, preserving needed files and output. Keep unrelated Temporal histories and the namespace intact.
3. Reconcile old provider targets while their IDs are still available. Close or explicitly decommission obsolete targets through the old runtime/provider after preserving needed disks and data. The SQL reset does not delete VMs or external machines, and the new inventory will not automatically adopt orphaned targets. Stop registered daemons and all application writers/workers, including optional services, then confirm the coordinated recovery point. Do not use a whole-database reset or `./dev.sh reset` for this upgrade.
4. Using the **v0.5.0 runtime** with the existing `LIGHTSPEED_POSTGRES_URL` and retained secrets, run:

   ```bash
   lightspeed-runtime migrate
   lightspeed-runtime schema-version
   ```

   Require schema revision 12 before starting services. Normal startup does not migrate. Each migration commits separately; migration 012 resets and recreates the environment tables in one transaction. It uses no cascading table drops, so an unexpected dependency fails the reset rather than deleting unrelated data. If migration fails, keep writers stopped and investigate; do not widen the drop scope or bypass checksum checks.
5. Update gateway origin configuration, provider configuration and any external receipt readers for protocol 4. Roll out matching runtime, Platform, Configurator, connectors and clients from one manifest. Platform retains its database and applies its own migration checks on startup. Rebuild Incus templates with the matching envd; upgrade existing external/registered daemons deliberately. Passive Incus guests do not use outbound automatic upgrade. For outbound automatic upgrade, first provide a valid deployment discovery document and archive URLs; publication alone does not install that route.
6. Recreate deployment providers, universe bindings, registration keys and environment credential bindings. Recreate provisioned/external environment records and register daemons with new registration secrets. Review daemon state paths explicitly; old enrollment keys and runtime environment IDs are not migrated. Update session/profile environment attachments and registration-key allowlists to the new IDs. Keep old machine/daemon state backed up; retained identity or output is not a promise that an old job or transfer can resume.
7. Verify existing accounts, universe membership, sessions, workspace files, attachments and auth secrets, then exercise a small new environment job. Check provider create/close, registered reconnect, and any installed connector workflows before reopening ingress. Resume affected work as new operations only after checking for effects already performed. If recovery is necessary, restore the coordinated old recovery set with the old release; an image-only rollback cannot restore deleted environment records.

See [Upgrades and recovery](https://ls.bot/docs/deployment/upgrades-and-recovery/) for coordinated backups and recovery, [registered daemons](https://ls.bot/docs/environments/registered-daemons/) for enrollment, and the [environment protocol reference](https://ls.bot/docs/reference/environment-protocol/) for provider integration. The release-specific steps above replace the development reset advice in PR #124.

**Code mode and tool execution**

- Enable Code mode in a profile or idle session to compose existing tools in one `code_execute` JavaScript call, including independent concurrent calls, MCP discovery, environment jobs, sub-agents and promise controls. Execution limits, cancellation and partial-outcome reports bound the work; completed effects are not rolled back and the whole script is not automatically retried.
- Shared content references and blob tools support reference-based file writes, environment file references and persisted web-fetch bodies. Code mode's `text()`, `media()` and `file()` helpers select output for the model. Session resources show when Code mode is enabled.
- Codex-style tool presentations prefer patch editing; OpenAI Responses supports grammar-constrained freeform patch calls and replay of existing calls. Anthropic tool schemas no longer use rejected top-level alternatives for blob/file writer inputs; runtime validation still enforces the allowed input combinations.

**Sessions, workspaces and interface**

- Queued messages can be promoted to steering with their text and attachments intact. If the target run has already finished, the UI sends an idempotent follow-up. Ambiguous steering outcomes retain a recoverable copy and require explicit recovery to avoid duplicates; conversion is not an atomic runtime operation.
- Queued follow-ups no longer starve Temporal timers while a run waits on an await. Conversation activity distinguishes tool waits from approval waits and avoids attributing another run's cancellation to current work.
- Workspace files gain drag-and-drop moves and Markdown preview controls. Setup pages use shared inventory tables and details dialogs for environments, MCP servers and models. The UI bundles IBM Plex Sans and Mono.

**Environments and development**

- Registration keys can be edited and rotated, environments can be updated, and closed rows are hidden by default. Provider credentials are optional. The Incus provider owns idle policy and wake-on-dial.
- envd supports Unix socket listeners, strict JSON-RPC handshakes, confined filesystem resolution, atomic conditional writes and rename. Process/job output uses byte offsets with explicit gaps and exit outcomes. Fixes address output loss, paging, resubmission, blocked input, and expensive output rewrites.
- Local development uses Chainguard MinIO server/client images and preserves access to existing root-owned MinIO volumes.

**Validation limits**

The release preparation's database checks cover a fresh PostgreSQL installation and a seeded v0.4.0 ledger upgrade, including preservation of unrelated seeded records and rollback when an unexpected table dependency blocks the reset. They do not establish recovery of every historical session or Temporal history. Real Incus idle/wake/power behavior and an end-to-end deployed upgrade still require operator validation; PR #124 did not test against a real Incus server. This release does not add automatic conversion of old environment workflow histories or deployment orchestration.
